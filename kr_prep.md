# Подготовка к КР

## Когда я выберу rebase, а когда merge? Почему?
rebase — для своей локальной (ещё никем не используемой) feature-ветки: перед PR подтягиваю свежий main через `git rebase main` и «причёсываю» коммиты через `rebase -i`. История получается линейной и читаемой.
merge — когда сливаю общую/публичную ветку или важно сохранить факт интеграции (merge-коммит показывает, где ветка влилась). Пример: feature/calculator перед PR — rebase на main; влитие release-ветки в main — merge.

## Что произойдёт, если сделать rebase публичной ветки, с которой работают коллеги?
Rebase пересоздаёт коммиты с новыми хешами. У коллег останутся старые коммиты, их история разойдётся с удалённой: при pull появятся дубли коммитов и конфликты, а после `push --force` можно затереть чужую работу. Поэтому публичные ветки не переписывают — для отмены используют revert.

## Зачем нужен multi-remote и где он применяется?
Чтобы один репозиторий жил в нескольких местах: бэкап-зеркало (GitHub + GitLab/Gitverse), fork + upstream в open source (своя копия и оригинал), отдельный remote для деплоя (например, Heroku/сервер), миграция между хостингами без потери истории.
